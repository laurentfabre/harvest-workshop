Préparation

Huit participants travaillent individuellement avec leur compte, dans l’essai Harvest ou Avanade / Accenture.

  1. Se connecter avec son propre compte à l’essai de son organisation. Identifier le volume, le compute du notebook, le warehouse SQL et l’App Space utilisables avec ce compte.
  2. Vérifier l’accès aux sources du parcours et la possibilité de créer une application dans l’App Space. Identifier le compte qui exécute réellement les lectures.

  5. Dans Mon parcours, sélectionner son prénom. Utiliser son code personnel dans le notebook, puis saisir les liens de son essai et son schéma dans Mes accès.
  6. Exporter régulièrement le carnet. Les notes restent dans ce navigateur, sans synchronisation d’équipe. Les services Databricks nécessitent Internet ; le guide et les données téléchargées restent lisibles hors ligne.

Sources et règles

Sources : {{ns}}contract_observations et {{ns}}contract_review. Une ligne par contract_id au business_date 2026-10-20 ; six contrats, trois fournisseurs fictifs, trois familles de format. Ce snapshot résume des observations de conversion préparées ; aucun parseur de production n’est exécuté. contract_id est la clé, sans jointure nécessaire. supplier_cents = valeur fournisseur ; normalized_cents = résultat observé du mapping ; analytical_cents = estimation séparée. normalization_delta_cents = normalisé moins fournisseur. review_status : SOURCE_INCOMPLETE si fournisseur absent ; CONVERSION_FAILED si erreur ou normalisé absent ; VALUE_CHANGED si les valeurs diffèrent ; PRESERVED sinon. Mini-lab · Ontologie et couche sémantique

L’ontologie décrit les objets métier, leurs relations, leur identité et ce que leurs états signifient. Elle permet de demander « de quel contrat, de quelle échéance ou de quel calcul parle-t-on ? » avant de compter.

La couche sémantique associe à ce vocabulaire des règles exécutables : population, dimensions, unités, métriques et traitement des absences. Les mêmes définitions peuvent être réutilisées par SQL, Genie et l’app.

Laboratoire local sur le snapshot synthétique au 20/10/2026 à 10:00 UTC. Les comparaisons sont calculées par les SQL fournis lors du build, pas par une requête live du portail. Les raccourcis sont des hypothèses pédagogiques explicites, pas des erreurs attribuées à Genie.

Avant de révéler les résultats, prédisez : un montant normalisé prouve-t-il que la valeur fournisseur a été conservée ? Quel montant faut-il additionner ?

  2. 3 min · Explorez C002, C004 et C005. Nommez le contrat, le fournisseur, la version du mapping et les trois valeurs. Choisissez une relation et sa clé.

Objets et relations

  1. Fournisseur : L’émetteur de la valeur contractuelle ; il ne définit pas l’estimation analytique. Grain : Une identité provider_id. Source : {{ns}}contract_observations.provider_id ; objet logique, sans table fournisseur dédiée.
  2. Contrat : L’objet dont on veut préserver la valeur, observé à une date métier. Grain : Un contract_id dans ce snapshot à date unique ; une évolution multi-date exigerait contract_id + business_date. Source : {{ns}}contract_observations → {{ns}}contract_review
  3. Conversion observée : La valeur normalisée et l’erreur éventuelle, avec une version du mapping. Une observation ne prouve pas la cause. Grain : Une observation par contrat/date dans ce jeu ; pas d’historique d’exécutions. Source : {{ns}}contract_observations.mapping_version, normalized_cents, conversion_error
  4. Valeur & estimation : Trois rôles différents : fournisseur autoritatif, normalisé à comparer, estimation analytique indépendante. Grain : Trois attributs en centimes EUR ; NULL = preuve absente, jamais zéro. Source : supplier_cents / normalized_cents / analytical_cents
  1. Un fournisseur émet des contrats (1 → plusieurs) : provider_id identifie le fournisseur de chaque contrat.
  2. Un contrat possède une observation de conversion (1 → 1 dans le snapshot) : contract_id ; rattacher mapping_version et source_file, sans inventer un historique.
  3. La conversion compare des valeurs de rôles distincts (1 → 3 rôles, chacun nullable) : PRESERVED compare fournisseur et normalisé ; l’estimation ne participe pas à ce statut.

Définitions réutilisables

  1. Contrats conservés : Nombre de lignes dont review_status = PRESERVED. Le statut exige un montant fournisseur connu, aucune erreur, un normalisé connu et identique. Unité : contrats. Limite : Une conservation numérique n’autorise pas une livraison.
  2. Montant fournisseur conservé : Somme de supplier_cents pour PRESERVED, divisée par 100. Les valeurs analytiques ne remplacent pas les valeurs fournisseur. La complétude fournisseur est 100 × COUNT(supplier_cents) / COUNT(*) sur tous les statuts, distincte du taux de conservation. Unité : EUR. Limite : Somme d’une population vide = NULL ; montrer le nombre de montants connus.
  3. Taux de conservation : 100 × nombre conservé / nombre total de contrats. Réagréger numérateur et dénominateur ; ne pas moyenner les taux fournisseurs. Unité : %. Limite : Dénominateur nul = NULL. Une exclusion de statut change la question.

SA0

-- Hypothèse volontairement insuffisante : « normalisé » veut dire « conservé ».
-- Ce SQL décrit une lecture possible, pas un échec mesuré de Genie.
SELECT COUNT(*) AS population,
       COUNT(normalized_cents) AS treated_as_preserved,
       SUM(normalized_cents) / 100.0 AS normalized_eur
FROM {{ns}}contract_observations;

SA1

-- Définition commune : statut gouverné par contract_review ; montant fournisseur.
SELECT COUNT(*) AS population,
       COUNT(CASE WHEN review_status = 'PRESERVED' THEN 1 END) AS preserved_contracts,
       100.0 * COUNT(CASE WHEN review_status = 'PRESERVED' THEN 1 END)
         / NULLIF(COUNT(*), 0) AS preservation_pct,
       SUM(CASE WHEN review_status = 'PRESERVED' THEN supplier_cents END) / 100.0 AS preserved_supplier_eur,
       COUNT(supplier_cents) AS known_supplier_amounts,
       100.0 * COUNT(supplier_cents) / NULLIF(COUNT(*), 0) AS supplier_coverage_pct,
       SUM(supplier_cents) / 100.0 AS known_supplier_eur
FROM {{ns}}contract_review;

SA2

-- Réutiliser la même définition au grain fournisseur, sans moyenner les taux.
SELECT provider_id, COUNT(*) AS population,
       COUNT(CASE WHEN review_status = 'PRESERVED' THEN 1 END) AS preserved_contracts,
       100.0 * COUNT(CASE WHEN review_status = 'PRESERVED' THEN 1 END)
         / NULLIF(COUNT(*), 0) AS preservation_pct,
       SUM(CASE WHEN review_status = 'PRESERVED' THEN supplier_cents END) / 100.0 AS preserved_supplier_eur
FROM {{ns}}contract_review
GROUP BY provider_id
ORDER BY provider_id;

Question Genie avec le contrat

Utilise contract_review pour définir « conservé » comme review_status = PRESERVED, sans utiliser l’estimation analytique. Sources et règles

Sources : {{ns}}fund_expectations (une ligne par fund_id/nav_date), {{ns}}fund_observations (zéro ou une ligne par même clé), {{ns}}calculation_state (une ligne par calculation_id) ; vues {{ns}}fund_freshness et {{ns}}calculation_review. Mini-lab · Ontologie et couche sémantique

L’ontologie décrit les objets métier, leurs relations, leur identité et ce que leurs états signifient. Elle permet de demander « de quel contrat, de quelle échéance ou de quel calcul parle-t-on ? » avant de compter.

La couche sémantique associe à ce vocabulaire des règles exécutables : population, dimensions, unités, métriques et traitement des absences. Les mêmes définitions peuvent être réutilisées par SQL, Genie et l’app.

Objets et relations

  1. Fonds : L’entité métier ; son identifiant ne suffit pas pour joindre des observations couvrant plusieurs dates. Grain : fund_id ; une seule nav_date par fonds dans ce jeu. Source : {{ns}}fund_expectations.fund_id
  2. Échéance attendue : L’obligation de recevoir une VL à une date et une heure, selon le calendrier. Une non-attente reste visible. Grain : fund_id + nav_date ; expected, deadline_utc. Source : {{ns}}fund_expectations
  3. VL reçue : Une valeur, son heure de réception et sa version fournisseur. L’absence est une relation vide, pas une valeur à zéro. Grain : Zéro ou une observation pour fund_id + nav_date dans ce snapshot. Source : {{ns}}fund_observations → {{ns}}fund_freshness
  4. Calcul consommateur : Un résultat antérieur, son unité et la version qu’il a consommée. Plusieurs calculs peuvent dépendre du même fonds. Grain : calculation_id ; fund_id est non unique. Source : {{ns}}calculation_state → {{ns}}calculation_review
  1. Un fonds suit un calendrier de VL (1 → 1 échéance dans ce snapshot) : Le calendrier définit le dénominateur des VL attendues.
  2. L’échéance peut être satisfaite par une observation (1 → 0..1) : LEFT JOIN sur fund_id ET nav_date ; garder les lignes absentes et l’heure de référence.
  3. Une version fournisseur alimente plusieurs calculs (1 → plusieurs ; source parfois absente) : Comparer consumed_source_version à source_version ; compter les calculation_id séparément des fund_id. La jointure actuelle par fund_id est limitée au snapshot à date unique.

Définitions réutilisables

  1. VL attendues en retard et non reçues : Nombre de lignes de fund_freshness dont arrival_status = MISSING, au 20/10/2026 à 10:00 UTC. Unité : fonds/date. Limite : WAITING, NOT_EXPECTED et LATE_RECEIVED ne sont pas des absences encore en retard.
  2. Taux d’absences en retard : 100 × MISSING / nombre de lignes expected = 1. Le calendrier donne le dénominateur ; ne pas compter les lignes de calcul. Unité : % des VL attendues. Limite : Dénominateur nul = NULL ; pas de rafraîchissement live implicite.
  3. Calculs candidats et fonds concernés : COUNT DISTINCT calculation_id, puis COUNT DISTINCT fund_id, limités à RECOMPUTE_CANDIDATE. Deux mesures de grains différents. Unité : calculs / fonds distincts. Limite : Ce sont des candidats à examiner ; aucune exécution ni fermeture transitive du graphe.

SB0

-- Deux raccourcis volontairement insuffisants : absence = incident ; ligne jointe = fonds.
SELECT
  (SELECT COUNT(*) FROM {{ns}}fund_expectations e
   LEFT JOIN {{ns}}fund_observations o ON e.fund_id = o.fund_id AND e.nav_date = o.nav_date
   WHERE o.fund_id IS NULL) AS absent_observations,
  (SELECT COUNT(*) FROM {{ns}}fund_expectations e
   LEFT JOIN {{ns}}calculation_state c ON e.fund_id = c.fund_id) AS joined_rows;

SB1

-- Grain fonds/date ; le calendrier et l'heure figée définissent le retard ouvert.
SELECT COUNT(*) AS population,
       COUNT(CASE WHEN expected = 1 THEN 1 END) AS expected_funds,
       COUNT(CASE WHEN arrival_status = 'MISSING' THEN 1 END) AS overdue_missing,
       COUNT(CASE WHEN arrival_status = 'WAITING' THEN 1 END) AS waiting_funds,
       COUNT(CASE WHEN arrival_status = 'NOT_EXPECTED' THEN 1 END) AS not_expected_funds,
       COUNT(CASE WHEN arrival_status = 'LATE_RECEIVED' THEN 1 END) AS late_received_funds,
       100.0 * COUNT(CASE WHEN arrival_status = 'MISSING' THEN 1 END)
         / NULLIF(COUNT(CASE WHEN expected = 1 THEN 1 END), 0) AS overdue_pct
FROM {{ns}}fund_freshness;

SB2

-- Grain calcul : plusieurs calculs peuvent concerner le même fonds.
-- Le candidat doit être examiné ; cette requête ne déclenche aucun recalcul.
SELECT COUNT(DISTINCT calculation_id) AS calculations,
       COUNT(DISTINCT CASE WHEN calculation_status = 'RECOMPUTE_CANDIDATE' THEN calculation_id END) AS recompute_candidates,
       COUNT(DISTINCT CASE WHEN calculation_status = 'RECOMPUTE_CANDIDATE' THEN fund_id END) AS affected_funds,
       COUNT(DISTINCT CASE WHEN calculation_status = 'WAIT_SOURCE' THEN calculation_id END) AS waiting_calculations
FROM {{ns}}calculation_review;
